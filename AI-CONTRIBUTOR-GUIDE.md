# AION — AI Contributor Guide

**Audience:** Any AI model (Claude, GPT, Gemini, local models, agents, copilots)
invoked to read, write, review, extend, or reason about this repository.

**Status of this document:** Operational. Binding on AI-assisted contributions
from the moment it is merged. It does not supersede `GRAMMAR.md`'s decision
log, `PHILOSOPHY.md`'s principles, or `MILESTONES.md`'s exit criteria — it
exists to make sure every AI touching this project *follows* them instead of
improvising around them.

---

## 1. Why this document exists

AION's biggest risk is not a bad idea. It's **erosion by a thousand helpful
edits** — an AI model, asked to "improve" or "finish" something, quietly:

- adds a language feature that was never logged as a decision,
- upgrades a status word (`Specified` → `Implemented`, `static` → `proof`)
  because the output *looks* like it works,
- "fixes" an example by making it more impressive instead of more correct,
- writes documentation that describes the toolchain as if M1–M5 already
  exist, or
- resolves an open design question unilaterally instead of flagging it.

Every one of those failure modes is individually small and collectively
fatal to a project whose entire value proposition is **claims that are
exactly as strong as their evidence.** This guide's job is to make that
failure mode structurally hard to fall into, for any model, on any task.

If you are an AI model reading this before doing work on AION: the single
most important sentence in this repository is in `PHILOSOPHY.md`:

> "AION does not ask users to trust generated systems blindly."

That includes systems generated by you. Nothing you write is exempt from
being checked, and nothing you write should ask to be trusted on your say-so.

## 2. Source-of-truth hierarchy

When documents conflict, or a task requires a decision no document has made
yet, resolve in this order:

1. **`GRAMMAR.md` §3 (Decision Log)** — binding and numbered. If a decision
   (`D1`, `D2`, ...) covers the question, it wins, full stop.
2. **`MILESTONES.md`** — governs *sequencing*. Even a good idea is out of
   order if it belongs to a later milestone than the one currently open.
3. **`SPEC.md`** — the normative description of the current language,
   derived from the decision log. If `SPEC.md` and `GRAMMAR.md` disagree,
   `GRAMMAR.md` is correct and `SPEC.md` has a bug.
4. **`PHILOSOPHY.md`** — governs *why*, and is the tie-breaker for judgment
   calls the other three don't settle mechanically.
5. **`README.md`** — orientation for newcomers. It should never say
   anything the other four don't already support. If it does, that's a
   defect to fix, not a source to cite.

**If a task requires a decision not covered by any of the above:** do not
invent one and proceed. Write it up as a proposed decision-log entry (see
§6) and stop there. An unresolved open question is a valid deliverable; a
silently-resolved one is not.

## 3. Non-negotiable rules

These apply regardless of task, prompt phrasing, or how confident the
request sounds.

### 3.1 No status inflation
Use the five-term vocabulary from `PHILOSOPHY.md` exactly:
**Specified → Implemented → Tested → Verified → Proven.** Never describe
something as one level when it has only earned the level below it.
Concretely:
- Code that runs but has no tests is **Implemented**, not Tested.
- Tests that pass are **Tested**, not Verified — Verified requires a defined
  checking mechanism against explicit properties.
- Nothing is **Proven** without an actual proof artifact from a verification
  backend. AION has none in v0.1–M4. Do not write or generate text implying
  otherwise, including in comments, commit messages, or docstrings.

### 3.2 No new syntax without a decision-log entry
Any change to lexical rules, grammar productions, keywords, or the guarantee
predicate catalog requires a new numbered entry in `GRAMMAR.md` §3 *in the
same change*, per **D10**. A grammar diff with no matching decision-log entry
is invalid and must not be produced, even as a "draft" or "for discussion."
Discussion drafts go in an issue or a scratch doc — never as a silent edit to
`GRAMMAR.md`'s EBNF.

### 3.3 No LLM in the parse or validate path — ever
Per **D9** and the M5 exit criteria: the lexer, parser, and semantic
validator must be fully deterministic. If you are an AI model asked to
implement or modify the parser, validator, or `TEST` interpreter: do not
introduce any call to a language model, embedding, or other non-deterministic
component anywhere in that code path, regardless of how it's framed ("just
for better error messages," "just for fuzzy matching identifiers," "just as
a fallback"). If a task seems to require this, stop and flag it — it likely
means the task doesn't belong at this milestone.

### 3.4 No milestone skipping
Check `MILESTONES.md` for the current position before starting work. Do not:
- write code-generation logic before M3's IR exists,
- add an AI-assisted tooling feature before M3 is complete (M5 is explicitly
  gated on this),
- implement `proof`-class guarantee support before a real verification
  backend is designed and logged as a decision.

If a task description asks for something out of sequence, say so explicitly
and either decline or propose the smallest in-sequence step that moves
toward it.

### 3.5 No example inflation
Examples (the conformance suite, `OrderService`, any future normative
example) exist to be **checkable**, not impressive. Do not:
- add constructs to an example that the grammar doesn't yet define,
- make an example "more realistic" in ways that introduce undeclared
  references, unchecked guarantees, or ambiguous role/action mappings,
- remove a deliberately-negative test case because it "looks like a bug."

Every example is either in the conformance suite (and must parse/validate
under the current grammar) or is clearly marked exploratory and excluded
from conformance claims. Never blur that line.

### 3.6 Cross-document consistency is mandatory, not optional
Any change to one of `README.md`, `SPEC.md`, `GRAMMAR.md`, `PHILOSOPHY.md`,
or `MILESTONES.md` must be checked against the other four before being
proposed as complete. This is explicitly an M0 exit criterion, and it does
not stop applying after M0 — treat it as a standing rule for every future
change to any of these five files. A change that updates the grammar but
leaves a stale example in `SPEC.md`, or that updates `MILESTONES.md`'s
position without updating `README.md`'s "what exists now" list, is
incomplete.

### 3.7 Fail closed, textually as well as semantically
**D1** (absence of `ALLOW` means denial) is a security principle about the
*language*. Apply the same instinct to your own outputs: when uncertain
whether something is allowed by the current spec, grammar, or milestone
scope, treat it as *not allowed* and ask, rather than treating silence as
permission to proceed.

## 4. Working procedure for any contribution

Follow this sequence for any non-trivial task, including tasks that arrive
as an open-ended prompt like "improve the parser" or "add a feature":

1. **Read `MILESTONES.md` first.** Identify the current milestone and its
   exit criteria. State, in your own output, which milestone the task
   belongs to. If it doesn't cleanly belong to the current milestone, say so
   before doing anything else.
2. **Read the relevant sections of `GRAMMAR.md` §3.** Check whether a
   decision already governs the area you're touching. Cite the decision
   number in your response if it's relevant.
3. **Check `SPEC.md` and the conformance example(s)** for anything your
   change would affect or contradict.
4. **Do the smallest correct unit of work**, not the most complete-feeling
   one. A milestone's exit criteria define "done" — stopping short of gold-
   plating is correct; stopping short of the exit criteria is not.
5. **Self-check against §3 of this document** before presenting the result.
6. **State what you did *not* do and why**, if the task implied a larger
   scope than what you delivered. Silence on scope reduction is itself a
   form of overclaiming.

---

## 5. Definition of "Done" for AI-assisted work

A contribution is done only when it can point to which milestone's exit
criteria it satisfies, in the language of `MILESTONES.md` itself. If a task
doesn't map to any stated exit criterion, that's a signal to either:

- tie it to the *next* uncompleted criterion of the current milestone, or
- flag it as a new candidate criterion for maintainer review (do not add it
  to `MILESTONES.md` yourself without that review).

"It works when I tried it" is not a definition of done anywhere in this
project. "It satisfies exit criterion X" is.

## 6. Template: proposing a decision-log entry

When a task surfaces a design question with no existing decision, produce
this instead of resolving it silently:

```markdown
### D[N] — [short title]

**Question:** [the open question, stated precisely]

**Options considered:**
1. [option] — tradeoffs: ...
2. [option] — tradeoffs: ...

**Recommendation:** [if you have one, with reasoning]

**Status:** PROPOSED — requires maintainer decision before merge.
```

Do not merge this directly into `GRAMMAR.md` §3 as a numbered, binding
decision. Only a human maintainer finalizes a decision number. Your job is
to make the decision easy and well-informed, not to make it.

---

## 7. Template: adding a conformance spec

New examples for the M0/M1 conformance suite should follow this shape so
they stay machine-checkable as tooling comes online:

```markdown
## [name] — [positive|negative] conformance case

**Purpose:** [what grammar/semantic rule this exercises]
**Decision(s) exercised:** D[n], D[m]
**Expected result:** [parses cleanly | rejected with diagnostic X]

```aion
[the AION source]
```

**Why this is well-formed / ill-formed:** [explicit reasoning, referencing
decision-log entries — mirror the style already used in SPEC.md §4]
```

Prefer additions that exercise a decision or rule **not yet covered** by the
existing suite. `OrderService` and `examples/role-override.aion` together
already cover the D2/D11 subject-override path — the latter is the dedicated
witness (a bare `ALLOW` shadowed by a role-scoped `DENY`) — so look for the
*next* uncovered decision rather than re-testing that one.

## 8. Anti-patterns specific to AI-generated contributions

These are failure modes seen repeatedly across AI-assisted projects; call
them out explicitly because they are easy to produce without noticing:

- **Confident scaffolding.** Generating a full parser/validator/codegen
  skeleton "to show the shape" when only M1 is open. Scaffolding that
  implies later milestones exist creates false signal about project
  maturity. Build only the current milestone; leave later ones absent, not
  stubbed-and-pretending.
- **Helpful scope creep.** Adding a feature (a new obligation type beyond
  `AUDIT`, a new guarantee predicate, a convenience keyword) because it's
  easy to add and seems obviously useful. Easy-to-add is not the bar;
  logged-decision is the bar.
- **Rewriting philosophy to justify code.** If an implementation choice is
  hard to reconcile with `PHILOSOPHY.md`, the fix is to change the
  implementation or raise the tension explicitly — never to quietly reword
  `PHILOSOPHY.md` to fit what was already built.
- **Marketing language drift.** Words like "powerful," "seamless,"
  "production-ready," "intelligent," or "automatically ensures" have no
  place in this repo's docs unless a specific mechanism backs them. Prefer
  the flatter, checkable language already used in `SPEC.md`/`GRAMMAR.md`.
- **Silent example divergence.** Editing `SPEC.md`'s example without
  re-verifying it still round-trips through the actual grammar in
  `GRAMMAR.md` (see the `refund.amount <= payment.amount` field-reference
  issue as the canonical example of what to catch before merging, not
  after).

## 9. What "realtime, usable programming language" actually requires from here

The end goal — AION as a real, runtime-usable language — is reached by
milestone discipline, not by acceleration. Concretely, the fastest safe path
is:

1. Close M0 cleanly: the grammar/example contradictions are resolved and the
   D2 override test case now exists (`examples/role-override.aion`); the
   remaining M0 item is the licensing decision, which is the copyright
   holder's to make.
2. Build M1 against exactly the current grammar — no more, no less. A parser
   that accepts more than `GRAMMAR.md` defines is a bug, not a feature.
3. Let M2's validator be the first thing that can say "no" — this is the
   actual proof the language has semantics, not just syntax.
4. Resist adding a second code-generation target until M4's first target
   fully round-trips with a traceability report. Breadth before depth here
   will produce two half-working backends instead of one working one.
5. Treat M5 (AI-assisted tooling) as a strict reward, not a shortcut: it
   only turns on once M3's IR is stable, and only ever sits above it.

An AI model working on this project should treat "moving fast" as "closing
the current milestone's exit criteria correctly," not as "producing more
artifacts." The project's credibility — and its actual path to a working
runtime — depends on that distinction being kept, especially under the kind
of well-meaning pressure that produces the anti-patterns in §8.

## 10. Quick checklist (paste into any AI task before submitting output)

- [ ] Milestone identified; task is in-sequence or explicitly flagged as not
- [ ] Relevant decision-log entries checked and cited
- [ ] No new syntax added without a `PROPOSED` decision-log entry
- [ ] No status word used beyond what's earned (Specified/Implemented/
      Tested/Verified/Proven)
- [ ] No LLM introduced into parse/validate path
- [ ] Conformance examples still parse against the current grammar exactly
      as written (not "should probably" — actually checked, field by field)
- [ ] All five core docs re-checked for new contradictions
- [ ] Scope explicitly stated, including what was deliberately left out
